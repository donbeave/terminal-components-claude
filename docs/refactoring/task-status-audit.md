## 1. Method

**How done-ness is really established for this catalog.** Per `refactoring-tasks/terminal-components/README.md` and `docs/refactoring/plan.md` §6–7, a task is done only when (a) the pinned **standalone** `taskfmt verify` (explicit root/task-dir/immutable base) exits 0 with final line `DONE` on an isolated worktree, (b) the host creates a content-addressed **receipt** binding product digest, producer task, accepted source tree, harness/catalog digests, oracle SHA and reviewer decision, and (c) the verified tree is **integrated** onto the recorded parent (`git update-ref` with expected-parent check), giving the task usable ancestry for its dependents. The automated dispatcher/promotion lifecycle hardcodes `main` and must not be used. No task authorizes pushes, merges, oracle repinning or approval of changed output.

**Why `status = "pending"` is correct everywhere.** The mutable `status` field in `task.toml` is deliberately not the done-ness signal; all 73 packages say `pending` because the execution campaign has not started on holla (readiness is not accepted — re-audit open per `docs/refactoring/plan.md` §1). This audit therefore does not re-adjudicate package status; it re-checks each task's *premise* against the plans and main's actual state.

**73 vs 74 correction.** `ls refactoring-tasks/terminal-components/completion/` prints 74 entries because it includes the group `README.md`; the task packages are `001/`–`073/` and `task-index.tsv` has 73 data rows. TASK-074 does not exist. Earlier "74 dirs/packages" phrasing is a counting artifact, flagged in `plan.md` §6/§12.

**Verdict meanings.** `open` — no main counterpart; holla-era work not started. `main-partial-needs-port` — main has related work but it is incomplete or defective (missing piece or BFxx cited). `main-done-needs-port` — main completed the substance (commit/path cited); port + oracle re-verification only. `needs-decision` — premise genuinely conflicts with an accepted decision; the needed decision is stated. Port-candidate references (PC#1–PC#10) point at the table in `docs/refactoring/main-port-analysis.md` §4.

Per wave: Qualified proof (4): 4 partial. Immutable preparation (7): 1 open + 6 partial. Attribution foundation (1): 1 partial. Reusable system (23): 19 partial + 4 done. Applications (33): 4 open + 29 partial. System closure (5): 1 open + 3 partial + 1 needs-decision.

**Most important alignment findings:**

1. **The Reusable system wave (009–031) is the reuse reservoir and the repair reservoir at once.** All 23 tasks have substantial main counterparts (4 effectively done: layers, dialogs/menus, static chrome, help/wizard), and all fourteen BF defects land inside this wave — 013 carries six of them (BF01–BF06, BF09). Porting the library and repairing it must be one operation (PC#1–PC#4); porting without the BF list imports source-proven defects, two of which are frozen by tests that assert the wrong behavior (BF08, BF12).
2. **The Applications wave gets mechanics from main, not evidence.** Shells, constructors and routing patterns are portable (PC#7), but every app task still needs oracle-driven restoration: main's app evidence is self-blessed (`0191acbf`), and its coverage is short everywhere (Showcase 22/23, Holla 11/34, simplified Jackin Settings/Usage, TablePro's reduced query editor). The four closure tasks (039/050/057/064) and the merge receipt (069) have no main analogue at all — the proof/receipt machinery is genuinely new.
3. **The Qualified proof wave should mine main's tooling as reference implementations, not as products.** `parity_replay.py`, capture scripts and the xtask boundary/doc-check suite (PC#5) embody hard-won discipline (fail-closed bless-guard, classification ledger, parallel replay), but the tc-proof host/receipt/context model has no main counterpart, and the tui-snap PR #1 head `883d03f` remains the hard external blocker for 001/070–072 and everything downstream.
4. **Two premise conflicts with goal history need adjudication, not silence.** TASK-066 mandates one render target while main's accepted Adjudication P2 made the two-target split contractual (CI names both) — an explicit counter-adjudication is owed. TASK-008's premise (no candidate-side test authority) is the proof contract's deliberate override of `main:GOAL.md` Phase 4's "reviewed baseline updates" — the contradiction is recorded in `goal-evolution.md` and `plan.md` §12, and main's self-blessing `0191acbf` is exactly the anti-pattern 008 exists to disposition.
5. **Holla-era behavior encoded in tasks must not be overwritten by main ports.** Tasks 014 (truthful scroll + fades), 016/022 (one-click editing, current-cell completed-click) and 040–049 (34 Holla worlds/HP journeys) encode behavior that post-dates main's integration reference `794b095c`; main treated it as out of scope, which is historical, not a defect. The reconciliation in `goal.md` §6 (behavior from holla, architecture from main) governs: ports into these tasks are behavior-selective merges with holla-first re-verification, never wholesale replacement.
