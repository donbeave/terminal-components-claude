## Preserved foundation

App separates update(&mut self,Cx) and draw(&self,Ui); Response independently represents consumption and None/Paint/Layout invalidation. Id roots/segments are namespaced/kind-delimited, ItemKey supports numeric/text/composite keys, PartRef preserves component versus subregion identity. Runtime centralizes focus, press/capture, pointer dispatch, wheel barriers, layer lifecycle and cursor. Ui scopes clipping, registrations, styles and derived geometry. These should be completed, not replaced with historical app-local interaction machines.

## Source-proven gaps and dependency order

1. **RT-TIME: event-count time and disconnected scheduler.** runtime.rs:994-1002 advances clock by theme.motion.tick_ms for each Tick; Cx has update_cause (cx.rs:294) but no now timestamp. Terminal session schedules repaint_after durations using Instant, independently of that virtual clock (session.rs:159-204). A requested 2,200ms deadline yields one fixed-cadence clock step after 2,200 real ms. Route-specific Jackin clock advances are consequently app-owned. Add explicit monotonic timestamp handling, expose immutable now through Cx, store absolute deadlines, provide deterministic harness advance-to. Terminal supplies elapsed monotonic time; arbitrary inputs and draw counts never advance time. Motion policy must govern animation, not elapsed domain deadlines. Existing tests headless_tick_uses_the_same_update_cause_without_wall_clock and bootstrap_runs_once_before_first_draw_without_a_tick encode the obsolete convention and need obligation-preserving replacement.

2. **RT-FLASH: activation flash can remain forever.** runtime.rs:733 creates inter.flash expiration. wants_tick includes flash (runtime.rs:239), but terminal loop never consults it: next_deadline only returns services.repaint_after (runtime.rs:264). Idle button-only application receives no Tick, so clock never expires flash. Also Button::update (button.rs:280-309) emits activation for keys without shared feedback registration. Runtime must own an activation-feedback semantic request and min(app deadline, flash deadline) scheduling. Prove mouse and keyboard feedback starts once, expires at reference time without unrelated inputs, schedules one repaint, and paused/reduced motion obeys approved contract.

3. **RT-GEOMETRY: queued input consumes incompatible presented facts.** session.rs:172-183 drains all ready events before drawing. Resize clears interaction/cache but retains registry and ring (runtime.rs:446-461). Route-changing update likewise cannot publish new geometry until draw. The next queued pointer event resolves last.registry (runtime.rs:572), possibly for old route/viewport. Handle before first draw bootstraps update but has no geometry. Fix presented-frame lifecycle: explicit initialization, geometry/layout validity generation, and a rendering/commit barrier before further geometry-dependent queued input whenever geometry can change. Distinguish what has actually been presented from proposed layout; do not silently dispatch using speculative unseen UI. Public headless/runtime API must enforce same precondition or explicitly defer input, not rely solely on terminal-loop discipline. Regression sequences: first pointer before frame; resize then click queued without interim draw; route change then click; removed control then release; modal opening then wheel/drag/key; heights 30/31. Current Harness auto-draws every input (harness.rs:83), masking the terminal batching defect.

4. **RT-PURE: runtime draw invokes update.** draw_with_buffer runtime.rs:1106 calls ensure_bootstrap; ensure_bootstrap calls app.update via run_update (939-952). A production fixture's first render can commit domain changes/open layers/run effects through that call despite App::draw shared reference. Split explicit initialize/update lifecycle from pure production-view rendering and test model/effect counters before very first draw, repeated draw, resize render, and focused-edit render. Current conformance snapshots state only after Harness::new has already drawn twice and bootstrapped (driver.rs:407; harness.rs:49-62), so it cannot detect this class. Shared-reference signature/static scan alone is insufficient.

5. **RT-HOVER: stale hover survives movement of same owner.** draw_with_buffer comment claims re-resolution, but runtime.rs:1186-1194 only clears hover if owner vanished; it stores no last pointer position. Move/reorder within same owner or a retained owner moving away leaves old PartRef highlighted until next pointer move. Store last physical pointer position and re-hit against committed geometry (while preserving keyboard suppression); test stationary pointer with list sort/filter, owner moving, clipped row disappearing and layer opening.

6. **RT-ID: dynamic menus cannot preserve identity.** MenuState.cursor/open are usize (menu.rs:129-132), ContextMenu rows unconditionally ItemKey::index and explicitly assume static declarations (menu.rs:435-436). This is valid only for truly static chrome; dynamic application menus require keyed menu items/open selection, explicit reconcile and logical submenu identity. Do not change every fixed positional decoration; migrate dynamic collections and prove insert/delete/reorder/disabled-state changes preserve the selected logical item and any pending destructive target. Jackin accounts/manager set_cursor(...ItemKey::index(...)) and TablePro selected usize fields require application-owner audit; source occurrence alone does not prove each is dynamic.
