# Runner qualification extensions: context authority, accounting, performance and native geometry

This is independent planner-owned preparation for VF-03, VF-04, VF-05 and PARITY-FINAL-04. It is not terminal-components implementation, a production harness acceptance, or permission to modify original oracle assertions. The existing runner bootstrap entrypoint automatically runs these files; there is no optional flag that production acceptance may omit.

Freeze these exact files together outside candidate write scope: `runner-bootstrap-driver.py`, `runner-bootstrap-app.py`, `runner-bootstrap-worker.py`, `runner-bootstrap-index.py`, `runner-bootstrap-extensions.py`, `runner-bootstrap-accounting.py`, `runner-bootstrap-native.py`, `runner-bootstrap-performance.rs`, both runner protocols, and the reviewed `host-bootstrap-observer.py`. TASK-070 owns the index/native/extraction groups, TASK-071 owns accounting and stage transitions, and TASK-072 owns performance measurement qualification. The separately prepared architecture bootstrap remains an additional TASK-072 prerequisite.

## Shared invocation and observer boundary

The existing commands and group spelling are unchanged:

```sh
python3 /task/trusted/runner-bootstrap/runner-bootstrap-driver.py --runner /work/tools/refactor-proof/bin/tc-proof --group 070
python3 /task/trusted/runner-bootstrap/runner-bootstrap-driver.py --runner /work/tools/refactor-proof/bin/tc-proof --group 071
python3 /task/trusted/runner-bootstrap/runner-bootstrap-driver.py --runner /work/tools/refactor-proof/bin/tc-proof --group 072
```

The original runner result schema is unchanged. The protected operator supplies context hashes, source/run identity, output path and inherited observer pipes. The submitted runner has read access only to its executable, public fixture inputs and explicitly permitted runtime paths. It may write only its output directory. Private source, instruments, original assertions, compiler products and in-memory observations are inaccessible. Both worker and submitted-runner sandboxes use default-deny file reads with narrow runtime/source exceptions. A same-account writable log is never execution authority.

Extension contexts use the original `tc-proof-runner-context/v1` plus one mandatory `qualification` object whose schema is `tc-proof-runner-extension/v1`. Its family is exactly `accounting`, `performance` or `native`. The protected context hash authorizes the family and all operation-specific fields; a production candidate cannot select preparation mode, alternate expectations, or a fixture family by editing its checkout or environment. Production campaign membership remains closed. These are supported operator-owned qualification inputs to the real command dispatcher, not a candidate-accessible alternate success path.

The extension observer accepts the original five-field `tc-proof-runner-observe/v1` request. It performs exactly one protected operation for each extension invocation; the native operation contains its complete unchanged-native and resized-transcript executions. This does not replace the separate original oracle-repeat cases, which still require two fresh requests and exact repeat equality. Every extension returns an observed object with exact operation/run/tree/source identity and `payload`. The private copy and its canonical digest remain authoritative. Successful outputs are exact observations; accounting additionally returns an exact `unresolved` array of fully qualified failing identities. Negative outputs are empty with the category specified below. The fixture requires actual observation even for its negative cases, so a category lookup without execution cannot qualify.

## Immutable check index — TASK-070 / VF-03

The normative index schema is `tc-proof-context-index/v1`, shared with the host fixture. Exact fields are `schema`, `run_id`, `task_id`, `tree`, `trust_sha256`, and `members`. Each member contains exactly:

```json
{
  "check_id":"CHK-002",
  "context_path":"operator-owned absolute child path",
  "context_sha256":"exact child byte digest",
  "schema":"tc-proof-runner-context/v2",
  "operation":"capture",
  "lane":"direct",
  "namespace":null,
  "required_ids":["complete ordered protected membership"],
  "output_id":"CHK-002.result.json"
}
```

The index fixture's runner child schema is `tc-proof-runner-context/v2`: all v1 fields plus `task_id` and `check_id`. There is no child-embedded index hash, avoiding a hash cycle. The index pins child bytes; the protected host separately supplies `TC_PROOF_CONTEXT_INDEX`, `TC_PROOF_CONTEXT_INDEX_SHA256`, `TC_PROOF_CHECK_ID` and `TC_PROOF_TASK_ID`. Other child schema families, including the comparator's existing strict schema and the host's fixture checker schema, keep their own declared fields; the index binds them externally instead of pretending every operation shares one schema.

The runner must validate the entire index and its child set on every operation, not merely the selected child's local hash. Required checks, source/task/run/trust, operation, lane/namespace, required identities and unique output identities must agree. Every context file must be regular and single-link; missing/extra files, duplicate check/output identities, path substitution and unknown fields fail. The child's own schema and exact fields must match the schema declared by its index member; a newly hashed child containing an unsupported schema or an extra authority field is still invalid. A correctly hashed foreign child still fails its task/run/tree/check binding. The host publishes the index only after all child bytes are frozen and before verification starts. Child contexts are never rewritten between operations.

The real positive sequence is preflight, direct capture, PTY capture, then close over one frozen source campaign. Direct and PTY execute the production fixture through the protected observer. The driver privately accepts each result after validating actual execution, stores its canonical digest, and supplies the accepted records to closure. Close must join all three prior check IDs exactly once, with their exact context and output identity. It rechecks completed output bytes against the independently accepted digests. It cannot create missing records, substitute another check's result, or treat its own success text as a prior receipt.

The finite index corpus rejects missing/extra children, swapping direct/PTY children, a correctly hashed child from another run/tree/task, independently rehashed wrong-schema or extra-field children, output aliasing, replaying one child under a second ID, mutation between operations, a failed member at closure and mutation of an already accepted output. Index/member failures use `CONTEXT_INDEX`; incomplete/failed/changed result joins use `CLOSURE`. Every negative is followed by a fresh complete positive sequence. Preparation self-tests execute the direct/PTY sequence and independently test both failed-member and changed-output closure.

## Original assertions, preparation accounting and actual closure — TASK-071 / VF-04

The fixture contains real original assertion source committed into a private Git history, its unchanged archived bytes, an actual production module, a candidate test source, and two independently executed test targets. Identities include source commit, package, target, profile and test name. The two targets deliberately share both test names, so name-only set matching cannot pass. The observer launches each real unittest suite separately without fail-fast and captures actual passed/failed/error/skipped outcomes; fixture profile labels test identity/accounting, not a claim that Python is a Rust MSRV compiler.

The operator freezes original source SHA-256, exact AST-qualified test spans, individual test-body digests, and the non-test byte projection. Candidate source with an unchanged test name but a no-op assertion fails. Approved replacement is a separate exact frozen digest: the positive retains the compatible original assertion and adds a stronger assertion. Outside-span production edits, broadened candidate spans, skipped tests, altered archives, duplicate identities, colliding qualifiers, source/run replay and a changed error classification fail. Real terminal-components span discovery still needs complete Rust parser/compiled inventory handling of inline modules/macros; this Python fixture qualifies the authority and preservation rule, not that Rust parser implementation.

`qualification.mode` is `preparation` or `production`, selected only by the protected host context. Production requires accepted inventory and disposition receipts. Preparation runs before those producer receipts exist and consumes an independent complete preparation register instead. Candidate proposals may describe observed inventory; they never authorize membership, replacement assertions, allowed failures or their own acceptance. A producer's proposed inventory must nevertheless match the independently required and executed qualified identities exactly: omissions, duplicates and foreign qualifiers fail even when the host independently executed the complete inventory. The positive proposal binds the actual original Git commit, not a stale temporary source identity. Missing preparation membership/disposition, a self-approval proposal, or using production mode without its required receipt fails. A valid preparation run without either future receipt passes using the already frozen independent register.

For TASK-008's approved migration, the driver first executes both complete original test targets on the exact prepatch parent **before the submitted runner is invoked**. It preserves those real all-green results. It then constructs the exact approved patch tree and independently executes **both complete postpatch targets before any submitted runner invocation or observer request**. The postpatch expectation register is derived from those actual outcomes, not literal expected status strings. The protected rehearsal record binds original parent, approved tree, original/patched assertion source, production-source hash, approved patch-manifest hash, profile-qualified process results and stdout/stderr identities. The driver verifies restoration of the separate submitted tree after constructing the approved tree.

The positive changes an obsolete future assertion from expecting the old production value to the oracle-required value; its actual postpatch rehearsal exposes a real assertion failure without altering the retained compatible assertion. The new failure is admitted only under the exact qualified future owner and recorded classification. The fixture rejects an unapproved new assertion/failure, swapping the approved patch, the wrong patch parent, hiding or truncating prepatch outcomes, absent postpatch rehearsal, forged postpatch outcomes, a forged derived register, or the wrong rehearsed tree. Rehearsal evidence resides in private driver memory before publication into the protected context. A submitted process cannot manufacture it. This is independent rehearsal before executor dispatch, not candidate self-approval of its modified tests.

All `future`, `closed`, unresolved and accepted-stage entries carry exact `(source_commit, package, target, profile, name)` identities. A future record additionally carries its fixed owner and failure classification. Bare-name matching is forbidden. The fixture's two same-name `test_future` assertions have distinct correction owners, and actual production behavior can correct either package independently. Positive mixed cases close tiny-a/unit/primary while tiny-b/integration/msrv remains legitimately unresolved, and vice versa. Borrowing another target's allowance, closure or correction owner fails.

The stage sequence starts with two real same-name future assertion failures. A real production correction closes only tiny-a while tiny-b still fails under its own allowance. A later correction closes both with an empty unresolved set, preserving the original assertions. Thus the qualified unresolved counts are exactly 2, 1, 0. The driver publishes synthetic stage receipts only after validating actual protected observations. Each disposable revision imports the same real archived Git bundle so the historical source identity remains exact across stages. A subsequent production regression fails; attempting to reopen the old allowance also fails against exact accepted closed identities and assertion lineage. Empty closure is an exercised positive, not a fixed requirement to keep a known failure forever. All accounting failures use `TEST_ACCOUNTING` in this extension.

Stage receipts use `tc-proof-accounting-stage/v1` and bind the observed run/tree, actual observation digest, original assertion-source digest, complete unresolved identities and complete closed identities. They contain no bare-name closure list. These are planner-owned synthetic acceptance inputs. Production uses host-owned accepted records with the full immutable task/source/receipt lineage in the main proof contract.

## Independent performance measurements — TASK-072 / VF-05

The fixture compiles the independently frozen Rust workload privately with the resolved real `rustc`, Rust 2024, `-Dwarnings` and `-Copt-level=3`, before any submitted runner call. It pins compiler, source and executable hashes. No candidate build script or benchmark code chooses the measurement instrument. The global allocator wrapper counts actual allocations and delegates to `System` with the original pointer/layout contract. Production `draw_frame` and `resolve_style` calls update independent atomic work/call counters. `Instant` measures nested style time and the complete frame workload; `black_box` keeps the measured workload live.

The observer performs three serial release executions in a fixed environment with strict mode enabled. The positive requires eight actual draws, eight style calls, eight allocations, the exact work count, nonzero nested timings and median style/frame time at most 5%. The synthetic ratio has a wide margin; it is a qualification perturbation, not a claimed measurement of Showcase. Real TASK-067 thresholds still require the accepted controlled machine/toolchain/profile and actual production workload.

The negative allocator perturbation performs sixteen real allocations. A heavy-style variant shifts nearly all measured work into style resolution. No-op and smoke-digest variants execute no production frame workload. Wrong denominator, candidate-owned counter attribution, debug/parallel profiles and disabled strict mode fail. These are observed measurements and source-bound profiles, not candidate-reported benchmark summaries. The observer's raw measurements remain visible; no timestamp masking or digest-only smoke result becomes performance proof. Failure category is `PERFORMANCE`.

Rust fixture policy is explicit: the allocator wrapper is the only unsafe boundary and documents its forwarding invariant; atomics do not allocate. The custom standalone fixture uses rustc warning denial, rustfmt and actual perturbation execution instead of pretending it belongs to the terminal-components Cargo workspace. It changes no terminal-components production implementation.

## Untrusted extraction seams and Holla native/resized separation — TASK-070 / PARITY-FINAL-04

The base capture corpus now executes constant-state, wrong-state, omitted-field and test-only-path extraction mutants. They cannot replace actual handler/draw observations, even when other frames are valid. The frozen candidate may contain extraction-only seams needed to expose its state; those seams are untrusted producer code, not an expected-state or assertion authority and not a prerequisite accepted candidate-adapter receipt. The baseline already owns the observation schema, identities and source-qualified expected meaning. Incorrect source binding remains independently rejected.

An explicit-seed positive also executes a protected seed transition through the real production update handler before the first captured checkpoint, then records complete before/after frames around the next real action. Wrong initial state and omission of the required seed transition fail. Real Jackin/TablePro seed adapters must likewise name the exact source fixture or real handler sequence, serialize its pre-action state and subsequent state, and prove its rendering uses that state. A descriptive world name cannot imply a constructor state which the source never creates: for example, a connection that opens a Query tab cannot be relabeled an empty Workbench. Such a state requires an explicit source-derived setup and its own before/after evidence. Candidates cannot choose a more convenient initial state or use copied expected bytes as the seed.

The native geometry fixture preserves real source-native fixed-row assertions: attached at row 38 in 120×40 and unavailable at row 28 in 100×30. Those exact original assertions execute at their original sizes; the runner never attempts to apply row 38 to a height-24 frame. A separate protected mapping derives the same footer owner as `height - 2` and its pointer anchor as `(2, height - 2)` at all four sizes, then executes the real pointer handler and captures complete frames. Candidate hit geometry cannot choose the mapping.

Native cases reject deleting an original assertion, changing its predicate, omitting the required mapping, retaining a fixed row 38 at other sizes, using candidate identity as mapping authority, wrong oracle coordinates, changed candidate hit geometry and retargeting the pointer to make the changed candidate succeed. The last case demonstrates that a successful candidate click at a candidate-selected coordinate is still wrong. All sizes, complete rows and pointer effects remain required; no region mask is used. Failure category is `SOURCE` for these native mapping/source cases.

The actual Holla preparation contract is [holla-route-expansion.md](../holla-route-expansion.md), with all source sites in [holla-route-sites.tsv](../holla-route-sites.tsv). Its concrete original footer/ARG owners and coordinate transforms are frozen separately. The tiny fixture qualifies the unchanged-native versus oracle-derived-resized rule; it does not claim to have executed all 986 Holla source sites or captured real Holla frames during planning.

## Owned comparison versus diagnostic capture

The immutable host/check context distinguishes the task-owned comparison set from the complete diagnostic capture set. Component tasks own complete direct component comparisons; their application PTY captures remain complete diagnostics whose future-owned mismatches stay failed. TASK-073 has no owned oracle frame and invokes no parity comparator. Empty owned membership is explicitly inapplicable, never a fabricated “zero matched, PASS” result. Capture transport completeness and parity comparison are distinct results, and partial contribution closure never closes its parent scenario. The comparator independently qualifies its own complete membership and mixed-result accounting; this runner extension grants it no exemption.
